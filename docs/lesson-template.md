# 学习章节模板

新增一篇学习资料时，复制下面的结构。目标是让读者在 10 分钟内知道“为什么看、看哪里、做什么、怎样算完成”。

## 章节标题

> 一句话结果：读者完成本节后，能够 ______，并提交 ______ 作为证据。

### 适合谁

说明前置知识和预计用时，不要用“适合所有人”。

### 先验收再阅读

列出本节的完成标准，最多 3～5 条。标准必须可观察，例如：

- 能从一个请求追到 5 个代码入口。
- 能跑出一份包含样本量和阈值的评测结果。
- 能解释某个依赖不可用时的用户可见行为。

### 场景与问题

用一个真实用户问题或故障开场，说明如果不做这个设计会发生什么。不要从 API 名称开始。

### 代码入口

只列本节必须阅读的文件，并说明每个文件负责什么：

```text
path/to/Entry.java     # HTTP 或任务入口
path/to/Policy.java    # 约束和边界
path/to/Adapter.java   # 外部依赖适配
```

### 设计卡

```text
输入：
核心流程：
关键不变量：
失败路径：
观测信号：
```

### 跟做步骤

每一步只写一个动作，并给出预期结果。命令、页面操作和代码阅读要分开写。

### 证据要求

说明需要保存什么：命令输出、测试名、日志片段、页面截图、指标 JSON 或设计图。不要要求读者“自行验证”。

### 作业

作业应比跟做多一个小变化，但仍然能在 30～90 分钟内完成。写清输入、输出和验收标准。

### 参考答案 / 思考方向

开源资料不隐藏答案，但可以先给提示，再给关键判断。答案的重点是边界和取舍，不是复述代码。

### Badcase

至少列出一个最容易失败的场景，并链接到 [Badcase 卡片](badcases.md)。

### 一句话带走

用一句可复述的话总结本节，例如：

> 就绪检查回答“现在能否承接完整能力”，降级策略回答“部分依赖不可用时还能否安全地完成有限任务”。

## 写作检查表

- [ ] 标题能直接说明能力，而不是“源码解析”。
- [ ] 开头有可观察的结果和预计用时。
- [ ] 有明确代码入口，不要求全仓库通读。
- [ ] 至少有一个命令、测试或页面动作。
- [ ] 有失败路径和边界，不只描述 happy path。
- [ ] 有作业、产出物和通过标准。
- [ ] 新增术语第一次出现时给出项目内含义。
- [ ] 相关内容通过链接串起来，不复制整段技术说明。
