# 面试评分双人标注教程

本文说明如何为模拟面试收集可用于模型校准和发布门禁的人工标注。目标不是给网上面经打分，而是让两名评审对项目产生的真实面试回答独立评分，再用结果检验模型评分是否可靠。

## 1. 先理解数据流

```text
已结束面试
  ↓
筛选已回答、已评分的题目
  ↓
评审 A 盲评
  ↓
评审 B 独立盲评
  ↓
按题目聚合人工分数
  ↓
与模型原始分数和置信度比较
  ↓
生成评测指标和发布门禁结果
```

一条合格样本至少包含：题目 ID、模型原始分数、模型原始置信度、两名评审的分数，以及人工分数跨度。回答原文只在管理员盲评队列中短暂展示，不进入 replay JSON，也不应提交到 Git。

## 2. 标注前的准备

### 2.1 样本范围

只选择已经收卷的面试：会话状态必须是 `COMPLETED` 或 `CANCELLED`，题目必须有回答和模型分数。不要标注尚未结束、没有回答或评分失败的题目。

建议首批准备 30～50 条，覆盖：

- 基础题、项目深挖、系统设计、行为题；
- 低分、中分、高分回答；
- 模型低置信度样本；
- 用户主动反馈“评分不准确”的样本；
- 不同岗位、难度和面试场景。

不要只挑容易的回答，否则评测结果会虚高。

### 2.2 评审人安排

每道题由两名不同的管理员独立完成。评审人不能查看：

- 另一位评审的分数和理由；
- 模型分数和模型置信度；
- 用户的准确/不准确反馈；
- 用户、候选人和会话身份。

默认队列已经开启 `blind=true`，并且每个 session 每次最多返回 1 道题，避免同一场面试主导数据集。

### 2.3 评审前统一口径

项目使用 0～10 分制，建议按照以下锚点评分：

| 分数 | 含义 |
| --- | --- |
| 0～2 | 与问题无关、基本错误，或关键结论完全相反 |
| 3～4 | 只有零散概念，无法形成可执行方案 |
| 5～6 | 覆盖部分关键点，但缺少完整链路、边界或落地细节 |
| 7～8 | 覆盖全部关键点，并能结合题目场景解释 |
| 9～10 | 除覆盖关键点外，还能说明边界、权衡、风险、验证方式或明显加分点 |

评分应基于回答本身，而不是候选人的简历、职位或评审人的预期。若回答存在关键安全、权限、数据一致性或可靠性错误，应按实际影响扣分，并在理由中写明。

## 3. 使用管理后台标注

### 3.1 打开标注队列

1. 启动后端和前端并登录管理员账号。
2. 打开 `/admin`，进入“面试评分校准”区域。
3. 在“双人标注队列”中查看样本。
4. 确认页面显示“盲评：模型信号暂不展示”。如果看到模型分数、置信度或反馈提示，先不要评分，检查是否误用了 `blind=false`。

队列只展示去身份化后的题目和回答，并自动脱敏邮箱、手机号。仍然要人工检查回答中是否含有姓名、公司内部地址、客户信息、密钥或其他敏感内容；发现后不要复制到理由或外部文件。

### 3.2 逐题评分

对每道题按以下顺序操作：

1. 先独立阅读题目和回答，不看模型信号。
2. 判断回答覆盖了哪些必要点、加分点和风险点。
3. 按 0～10 分锚点评分。
4. 在“评分理由”中记录可复核的证据。
5. 点击“提交标注”。

推荐的理由格式是：

```text
覆盖：工具调用、超时处理。
缺失：幂等键、权限边界和降级路径。
结论：关键链路完整但工程细节不足，给 6 分。
```

理由是质量审计材料，不能只写“感觉不错”“回答一般”这类不可复核的结论。理由最多 2000 字，尽量写事实和证据，不写个人身份信息。

### 3.3 第二位评审领取同一题

第二位评审使用自己的管理员账号重新打开队列。系统会排除该账号已经标注过的题，因此同一题可以被另一位评审领取。两位评审不应通过聊天、截图或后台列表交换分数。

同一评审人重复提交同一题是幂等更新，会覆盖自己的分数和理由；这不算新增一名评审。

## 4. 单条标注的 API 格式

前端会自动调用以下接口，也可以用 API 客户端复现：

```http
POST /admin/interview-evals/annotations/{questionId}
Content-Type: application/json
X-CSRF-Token: <当前会话的 CSRF Token>
```

```json
{
  "humanScore": 8,
  "rationale": "覆盖工具调用、超时和幂等处理；没有说明权限边界和降级方案，因此不是 9 分以上。"
}
```

字段规则：

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `questionId` | path 参数 | 队列返回的题目 ID |
| `humanScore` | integer | 0～10 |
| `rationale` | string | 可选，最多 2000 字；建议填写 |

接口只接受已回答且已评分的 `COMPLETED`/`CANCELLED` 会话。未登录、非管理员、题目未收卷或分数越界都会失败。

## 5. 生成双人汇总结果

两位评审完成后，在后台点击“运行双人 replay”，或调用：

```http
POST /admin/interview-evals/annotations/replay
Content-Type: application/json
```

```json
{
  "datasetVersion": "interview-human-gold-v1",
  "minReviewers": 2
}
```

系统会按题目聚合标注：

```text
humanScore = round(所有人工分数的平均值)
reviewerCount = 独立评审人数
humanScoreSpread = 最高人工分数 - 最低人工分数
```

例如评审 A 给 8 分、评审 B 给 7 分，汇总结果为 `humanScore=8`、`reviewerCount=2`、`humanScoreSpread=1`。原始理由保存在管理员标注记录中，评测数据库只持久化分数和指标。

如果没有达到两名评审，接口会返回冲突错误，不应通过手工修改 `reviewerCount` 绕过门禁。

## 6. CI 使用的脱敏 JSON

需要把评测结果放入本地文件或受保护的 GitHub Secret 时，格式如下：

```json
{
  "datasetVersion": "interview-human-gold-v1",
  "cases": [
    {
      "id": "question-123",
      "humanScore": 8,
      "modelScore": 7,
      "modelConfidence": 0.82,
      "reviewerCount": 2,
      "humanScoreSpread": 1
    },
    {
      "id": "question-456",
      "humanScore": 4,
      "modelScore": 8,
      "modelConfidence": 0.91,
      "reviewerCount": 2,
      "humanScoreSpread": 0
    }
  ]
}
```

每条 `cases` 记录必须满足：

- `id` 非空且稳定，建议使用脱敏后的题目 ID；
- `humanScore`、`modelScore` 是 0～10 的整数；
- `modelConfidence` 是 0～1 的数字；
- `reviewerCount` 至少为 2 才能作为发布 Gold；
- `humanScoreSpread` 是 0～10 的整数；
- 不包含 `answer`、姓名、邮箱、手机号、用户 ID、session ID 或评审人 ID；
- `modelScore` 必须来自当时的模型输出，不能用确定性规则基线冒充模型分数。

文件应放在被 `.gitignore` 忽略的目录，例如：

```text
evals/private/interview-score-gold-v1.json
```

本地运行门禁：

```powershell
$env:INTERVIEW_EVAL_BASE_URL="http://localhost:8180"
node evals/run_interview_score_eval.mjs `
  --input .\evals\private\interview-score-gold-v1.json `
  --min-reviewers 2 `
  --ci
```

如果结果的 `releaseEligible=false`，命令会返回非零退出码。不要为了让 CI 变绿而删除分歧样本或修改人工分数；应回到标注记录复核。

## 7. 质量门禁如何判断

当前门禁主要检查：

| 指标 | 默认要求 | 说明 |
| --- | --- | --- |
| MAE | ≤ 1.2 | 模型分数与人工分数的平均绝对误差 |
| 三级评分一致率 | ≥ 80% | 模型与人工分数处于同一评分区间的比例 |
| 明显高分误判率 | ≤ 5% | 人工低分但模型明显高估的比例 |
| 双人标注覆盖率 | 100% | 所有发布样本至少两名评审 |
| 评审分歧率 | ≤ 20% | 两位评审分差大于 1 的比例 |
| 高置信度大误差率 | ≤ 5% | 模型很自信但与人工差距仍很大的比例 |

评审分歧率过高时，先检查评分锚点是否一致，再对分歧题进行复审；不能只使用平均分掩盖意见冲突。

## 8. 数据安全和审计要求

- 只采集已取得授权的面试回答；
- 生产数据先去身份化，再进入评审队列或文件；
- Gold JSON 不提交仓库、不放在公开 Issue、PR 或聊天记录中；
- GitHub 使用 `INTERVIEW_SCORE_GOLD_JSON_B64` 受保护 Secret；
- CI 只在 runner 临时解码，任务结束后删除文件；
- 查看队列、提交标注和运行 replay 都会写入 `admin_audit_log`；
- 按项目数据保留策略定期删除原始回答和过期标注。

## 9. 常见问题

### 为什么队列里没有题目？

检查是否存在已回答且已评分的 `COMPLETED`/`CANCELLED` 会话，以及当前管理员是否已经标注过这些题。也可能是所有题目已经达到 `minReviewers`。

### 两位评审分数差很多怎么办？

不要私下修改成一致分数。保留两个独立分数，检查回答证据和评分锚点；必要时由第三位评审仲裁。当前门禁会通过 `humanScoreSpread` 和分歧率暴露这类问题。

### 可以只标注一位评审吗？

可以用于早期诊断，但不能作为正式发布 Gold。正式门禁要求每条样本至少两名独立评审。

### 网上面经能直接导入吗？

可以把公开面经改写成题目、追问和能力标签，但不能把作者的自述分数直接当作人工金标。只有对项目真实模型回答完成双人独立评分，才能进入正式评测集。

## 10. 完成检查清单

```text
[ ] 样本已授权，且会话已 COMPLETED/CANCELLED
[ ] 题目有真实回答和模型原始分数
[ ] 评审 A 独立盲标并填写理由
[ ] 评审 B 独立盲标并填写理由
[ ] 每条样本 reviewerCount >= 2
[ ] humanScoreSpread 已由系统计算
[ ] JSON 不含回答原文和身份信息
[ ] 本地 --ci 门禁通过
[ ] Gold 文件只存放在私有目录或受保护 Secret
```
