# 页面与数据加载性能优化记录

日期：2026-08-07  
范围：个人画像、能力差距、机会推送、成长计划页面及其后端数据链路

## 1. 优化背景

此前对页面接口进行实测，发现三个页面的慢点并不相同：

| 链路 | 冷启动表现 | 预热后表现 | 结论 |
| --- | ---: | ---: | --- |
| `/profile` | 约 4.1–5.5 秒 | 约 10–16 毫秒 | 首次 Spring MVC、连接池、JIT/WSL 通道预热造成抖动 |
| `/career/gaps` | 约 1.0–4.3 秒 | 约 35–50 毫秒 | Neo4j 冷连接、技能对齐缓存及图谱查询造成延迟 |
| `/notifications` | 约 9–33 毫秒 | 约 9–20 毫秒 | 当前数据量下不是主要瓶颈，需提前补齐增长期索引 |
| `/plans/today` | 约 8–18 毫秒 | 约 8–15 毫秒 | 页面查询本身较快 |
| `/plans/should-replan` | 首次约 300 毫秒 | 约 9–20 毫秒 | 原有两次数据库统计往返，可合并优化 |
| `POST /plans` | 可能几十秒 | 取决于 LLM | 同步等待 LLM，是成长计划操作的主要体验问题 |

## 2. 已完成优化

### 2.1 个人画像与能力差距

- 个人画像页的能力差距改为独立加载，不再让图谱链路影响基础画像展示。
- 增加能力差距区域的 Skeleton 加载状态和错误降级提示。
- `SkillAlignService` 将技能缓存查询由逐条查询改为一次批量查询。
- 未命中技能的 PostgreSQL 缓存回填改为批量写入，减少数据库往返。
- 应用启动完成后异步执行 Neo4j 轻量探活，提前建立连接。
- 保留 Neo4j 熔断降级：图谱不可用时返回当前可用缓存，不把临时故障写入 miss 缓存。
- 将 `DispatcherServlet` 改为启动阶段初始化，避免首个业务请求承担 Servlet 初始化成本。

涉及文件：

- `frontend/src/pages/ProfilePage.tsx`
- `backend/src/main/java/com/tutor/profile/SkillAlignService.java`
- `backend/src/main/resources/application.yml`

### 2.2 机会推送

新增 Flyway V15 索引：

```sql
CREATE INDEX idx_notifications_user_id_desc
    ON notifications (user_id, id DESC);
```

该索引覆盖“按用户查询最新通知”的主要访问模式，避免通知历史增长后出现用户范围扫描和排序退化。

### 2.3 成长计划

原实现为同步链路：

```text
HTTP 请求 → 调用 LLM → 解析计划 → 写入数据库 → 返回响应
```

现改为持久化后台任务：

```text
HTTP 请求 → 创建 queued 任务并立即返回 202
                         ↓
              后台领取任务并调用 LLM
                         ↓
              completed / failed 状态
                         ↓
              前端轮询并刷新今日任务
```

具体实现：

- 新增 `plan_generation_jobs` 任务表。
- `POST /plans` 仅负责入队，避免页面同步等待 LLM。
- 新增 `GET /plans/jobs/{jobId}` 查询任务状态。
- 后台任务使用 `FOR UPDATE SKIP LOCKED` 领取，支持多实例并发消费。
- 同时最多处理 2 个计划生成任务，避免 LLM 请求挤占主对话链路。
- 任务超过 10 分钟处于 running 状态时允许重新领取，避免进程崩溃造成永久卡单。
- 前端显示排队中、生成中、已完成和失败状态。

新增或修改文件：

- `backend/src/main/java/com/tutor/plan/PlanService.java`
- `backend/src/main/java/com/tutor/plan/PlanController.java`
- `frontend/src/pages/PlansPage.tsx`
- `frontend/src/lib/api.ts`
- `backend/src/main/resources/db/migration/V15__page_query_indexes_and_plan_jobs.sql`

### 2.4 查询与认证并发

V15 同时新增：

```sql
CREATE INDEX idx_plan_tasks_user_day
    ON plan_tasks (user_id, day, id);

CREATE INDEX idx_checkins_user_status_task
    ON checkins (user_id, status, task_id);
```

`shouldReplan` 的完成数和任务总数统计由两次数据库请求合并为一次请求。

前端认证请求增加 refresh single-flight 机制：多个接口同时遇到 401 时只发起一次刷新令牌请求，其余请求复用刷新结果，避免个人画像页多个并发请求触发刷新竞争。

### 2.5 Windows + WSL 前端代理

复测发现后端直连已经是毫秒级，但 Vite `/api` 代理仍有约 280–310ms 的额外耗时。原因是代理目标使用 `localhost:8180`，在 Windows + WSL 环境下会触发 IPv6/IPv4 回退。

已将 `frontend/vite.config.ts` 的代理目标改为：

```ts
target: 'http://127.0.0.1:8180'
```

修改并重启 Vite 后，前端 `/api` 请求降至约 10–40ms。当前开发环境建议使用 `http://127.0.0.1:5173` 访问前端；本机访问 `localhost:5173` 仍可能触发 Windows 的 IPv6 回退。

### 真实环境验证

验证环境：WSL Docker、PostgreSQL 16、Neo4j、Spring Boot 后端。

- Flyway 已成功从 V14 迁移至 V15。
- `/actuator/health`、`/profile`、`/career/gaps`、`/notifications`、`/plans/today`、`/plans/should-replan` 均返回 200。
- 预热后实测：画像约 10–16ms，能力差距约 35–50ms，机会推送约 9–20ms，计划查询约 9–15ms。
- WSL/Java 进程冷启动时仍可能出现一次几秒级延迟，该延迟主要来自 JVM、数据库连接、Neo4j 驱动和 Windows↔WSL 通道的首次预热，不属于稳定请求耗时。
- Vite 代理已切换至 IPv4，避免每个页面接口请求重复承担 `localhost` 解析回退。

## 4. 当前结论

本次优化解决了两个主要问题：

1. 个人画像页不再被能力差距图谱计算阻塞，能力差距链路在预热后已达到毫秒级。
2. 成长计划生成不再同步阻塞页面，LLM 慢响应转化为可观测、可恢复的后台任务。

机会推送和成长计划首页的普通查询本身已经较快，当前重点应放在数据规模增长后的索引监控，以及 LLM 后台任务的成功率、排队长度和耗时监控。

## 5. 后续建议

- 为页面接口增加 Micrometer 分段耗时指标，区分数据库、Neo4j、序列化和网络耗时。
- 为计划生成任务增加最大重试次数、失败告警和用户取消操作。
- 多实例部署时，将当前进程内的计划生成并发限制升级为共享队列或 Redis/消息队列协调。
- 若需要进一步降低冷启动时间，可继续优化 WSL Docker 启动顺序、Hikari 连接池预热和 Neo4j 图谱索引。
