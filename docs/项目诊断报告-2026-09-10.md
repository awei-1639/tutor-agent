## 1. 阻塞性环境问题（优先处理）

### 1.1 Maven 无法启动 —— **伪警报，撤回**

> **2026-09-10 15:35 二次修订**：本节初版（归因 `M2_HOME`）与修订版（归因 Git Bash + 原生 JDK 路径格式）**均已被证伪**。该问题不是项目缺陷，撤回该项。

`mvn` 在**某些会话**中失败：

```
错误: 找不到或无法加载主类 org.codehaus.plexus.classworlds.launcher.Launcher
原因: java.lang.ClassNotFoundException: org.codehaus.plexus.classworlds.launcher.Launcher
```

**真正根因**：当前 Bash 会话中注入了两个关闭 MSYS 路径转换的开关：

```
MSYS_NO_PATHCONV=1
MSYS2_ARG_CONV_EXCL=*
```

Maven 的 POSIX `mvn` 脚本用 MSYS 风格路径拼 classpath（`/e/maven/.../plexus-classworlds-2.9.0.jar`），正常情况下 MSYS 运行时会在调用 Windows 原生 `java.exe` 前把这类参数转成 `E:\maven\...`。这两个开关任一存在都会掐掉该转换，Windows `java.exe` 收到 MSYS 路径后无法解析，classpath 为空 → `ClassNotFoundException`。

逐一对照实验：

| 会话环境 | `mvn -v` |
| --- | --- |
| 完整继承环境（`MSYS_NO_PATHCONV=1` + `MSYS2_ARG_CONV_EXCL=*`） | FAIL |
| 仅去掉 `MSYS_NO_PATHCONV` | FAIL |
| 仅去掉 `MSYS2_ARG_CONV_EXCL` | FAIL |
| **两个都去掉** | **OK** |
| `env -i` 干净环境（仅 `HOME`/`PATH`/`JAVA_HOME`） | OK |
| 干净环境 + `M2_HOME=E:\maven\apache-maven-3.8.6` | OK |

结论：`M2_HOME` 指向旧的 3.8.6 在此处**完全不起作用**——因为 Maven 3.9 的 POSIX 脚本从脚本自身位置推导 `MAVEN_HOME`，`M2_HOME` 只是旧版兼容保留项。删掉或改对它，都不能修复（或破坏）`mvn`。

**为什么这是伪警报**：这两个变量是由当前的 **IDE Bash 工具**注入的执行环境（同时可见同源的 `CODEBUDDY_CONVERSATION_REQUEST_ID`），并非机器级配置。在用户自己的 PowerShell 或普通 Git Bash 终端里没有这两个变量，`mvn` 正常工作。

**在本会话内的绕法**（已验证 `mvn -o -B validate` 退出码 0）：

```bash
unset MSYS_NO_PATHCONV MSYS2_ARG_CONV_EXCL && mvn <goals>
```

或直接调用 `mvn.cmd`（Windows 批处理，不涉及 MSYS 转换）。

**遗留建议（低优先级）**：`M2_HOME=E:\maven\apache-maven-3.8.6` 与 PATH 中的 3.9.10 不一致，虽不影响本次现象，仍建议删除或改为 3.9.10 以免将来误用旧版本。注意：若已在系统设置中删除，旧终端因继承进程快照仍会读到旧值，需重开终端。

### 3.1 `LlmUsageRecorder` 的 null registry 隐患

```java
// LlmGateway 五参构造器 → new LlmUsageRecorder(jdbc, null)
registry.counter("tutor.llm.calls", ...).increment();   // registry 为 null 时抛 NPE
```

生产走 `@Autowired` 六参构造器，`MeterRegistry` 由 Spring 注入，不会为 null；但五参构造器（测试路径 / 缺少 Micrometer 的上下文）会传 null，每次调用都抛 NPE 再被 `catch` 吞掉记 debug 日志——用异常做控制流，且掩盖真实故障。建议加一行 `if (registry == null) return;`。

## 4. 安全

### 4.1 缺少全局异常处理 —— 高（相对本项目最重要的一条）

全仓只有 `ResumeController` 有局部 `@ExceptionHandler`，**没有 `@ControllerAdvice`**。后果：

- 未捕获异常走 Spring Boot 默认错误响应，与 `AuthInterceptor` 手写 `{"error":"..."}` 的 JSON 格式不一致，前端 `api.ts` 无法统一解析；
- `AuthInterceptor` 对 `/error` 直接放行（这是有意的，避免 500 被改写成 401），配合默认的 `server.error.include-*` 配置，存在泄露堆栈/异常消息的可能；
- 校验失败、参数绑定错误等没有统一错误码。

建议补一个 `@RestControllerAdvice`，统一返回 `{"error": "..."}` 并显式关闭堆栈与 `message` 外泄。

### 4.2 指标端令牌非恒定时间比较 —— 中

```java
// AuthInterceptor.java:46-50
if (path.equals("/actuator/prometheus") && !metricsScrapeToken.isBlank()
        && ("Bearer " + metricsScrapeToken).equals(req.getHeader("Authorization"))) {
```

`String.equals` 是短路比较，存在时序侧信道。改用 `MessageDigest.isEqual(a.getBytes(UTF_8), b.getBytes(UTF_8))`。

### 4.3 Admin 鉴权未下沉到 Controller —— 中

`AdminController`（`/admin/users/{id}/disable|restore|soft-delete`）、`KnowledgeDocumentController`、`InterviewScoreAnnotationController` 在 Controller 层均无鉴权，仅靠 `AdminService.requireAdmin()` 兜底。目前**是有效的**，但属于"靠人记得调用"的模式，新增 admin 端点容易漏。建议用自定义注解 + 拦截器，或在 `ArchitectureBoundaryTest` 里加一条 ArchUnit 规则：`com.tutor.admin..*Controller` 的方法必须标注 `@RequireAdmin`。

### 4.4 已确认安全的部分（无需改动）

- Actuator 只暴露 `health,info,prometheus`——**没有** `env`/`heapdump`/`beans`，这条配置是对的；
- `.env` 未被 git 跟踪（`git ls-files` 确认只有 `.env.example`），其中含真实 API Key 属本地正常用法；
- 无 `System.out.println` / `printStackTrace()`，无日志打印 token/password/secret；
- 业务端点已强制 401，`DEV_USER_ID` 仅出现在 `/internal/*` 与 `/auth|healthz|readyz`，符合约定；
- CSRF 拦截器豁免范围（`/internal`、Bearer、`/auth` 除 logout 外）合理；
- `docker-compose.yml` 默认口令 `tutor_dev_only` 仅限开发，文档已明确标注。

### 4.5 轻微

- `path.startsWith("/auth")` 会误匹配 `/authz` 之类的前缀（当前无此路径）；
- `/internal/*` 端点直接从 `req.userId()` 取用户，不与 token 比对，仅靠 loopback + `INTERNAL_ENDPOINTS_ENABLED` 保护；
- 无 HSTS / CSP 响应头（前端由 Nginx 注入 CSP，反向代理层已覆盖部分）。

## 5. 依赖生命周期 —— 高

`backend/pom.xml` 使用 `spring-boot-starter-parent` **3.4.5**。

Spring Boot 官方支持表：

| 分支 | 初始发布 | OSS 支持终止 | 当前状态 |
| --- | --- | --- | --- |
| 3.4.x | 2024-11 | **2025-12** | 已终止（末版 3.4.13） |
| 3.5.x | 2025-05 | 2026-06 | 已终止 |
| 4.0.x | 2025-11 | 2026-12 | 支持中 |
| 4.1.x | 2026-06 | 2027-07 | 支持中 |

也就是说：项目当前版本**已停止接收安全补丁超过 8 个月**，而且唯一还在 OSS 支持期内的路线是 4.x。

分两步走：

1. **立刻、低风险**：升到 `3.4.13`（3.4 分支最后一个版本，含 37 个 bug 修复与依赖升级）。改动面极小，先把已知修复吃到。
2. **立项、中风险**：规划 3.5 → 4.x 迁移。主要 breaking change 是 `@MockBean` 被 `@MockitoBean` 取代（测试代码改动量大）、`management.endpoint.*.enabled` 改为 access 模型、Jakarta/ Jackson 版本跳跃。

其他依赖：`langchain4j 1.0.1`、`springdoc 2.8.6`、`opentelemetry 1.45.0`、`jtokkit 1.1.0`、`jacoco 0.8.12`——版本较新，无 immediate 风险，随 Boot 升级一并核对兼容性即可。

## 6. 架构约定一致性

### 6.1 ArchUnit 规则有效 —— 好消息

`backend/src/test/java/com/tutor/architecture/ArchitectureBoundaryTest.java` 里写的包路径（`com.tutor.knowledge.retrieval..`、`com.tutor.knowledge.document..`、`com.tutor.platform.llm..` 等）**与重构后的实际包结构完全一致**，规则不是形同虚设。这点容易在包迁移后失效，值得确认一次。

### 6.2 LLM 调用未绕过网关

`dev.langchain4j` 仅出现在 `platform/llm` 包下 7 个文件中（`LlmJsonExecutor`、`EmbeddingProviderClient`、`ChatStreamProviderClient`、`LlmStreamingExecutor` 等），业务代码零处直接构造 provider 模型。约定被遵守。

补充说明：`LlmGateway` 在生产代码中**没有按类名被引用**（只在测试里被 mock），业务类注入的是 `EmbeddingGateway`/`JsonGenerationGateway`/`StreamingGenerationGateway`/`RerankGateway` 四个接口，`LlmGateway` 是唯一实现。所以它不是死代码，只是 `CLAUDE.md` 里"所有模型调用走 `LlmGateway`"的表述容易让人误以为是直接依赖——建议改述为"走 `LlmGateway` 实现的网关接口"。

ArchUnit 只约束 `*Controller` 不依赖 `llm..`，业务层（`ChatService`、`ExpertRunner`、`ToolCallLoop`、`CitationGuard`）仍直接注入网关接口。这是合理取舍，无需改。

### 6.3 Flyway

- 共 67 个迁移文件，**无重复版本号**；
- **V65 缺号**（版本缺口，Flyway 允许，非问题）；
- **V66 的提交时间（08-31 00:48）晚于 V67（00:47）**，`application.yml` 未开 `out-of-order`（默认 false）。任何在 00:47–00:48 之间已应用过 V67 的数据库，升级时会因版本乱序被拒。时间窗极窄，实际影响很小，但建议显式设 `spring.flyway.out-of-order=true` 或在 `docs/operations.md` 记录该历史。
