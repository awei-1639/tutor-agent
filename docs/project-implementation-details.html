1. 项目定位：把 LLM 放进可控工作流

LLM 处理不确定的语义，确定性代码处理可验证的边界。

LLM

理解与生成

意图建议、Query Rewrite、证据充分性判断、专家分析、回答生成、引用语义判断。

Code

边界与治理

身份、租户、Token、权限、Schema、超时、取消、幂等、降级、审计和发布门禁。

关键原则：模型输出不是可信指令。Router 要经过 RoutingPolicy，专家引用要经过来源验证，工具调用要经过 Registry 和 Executor。

2. 请求主链路：从 POST 到 durable result

ChatController 校验输入不超过 4000 字符，执行用户限流，读取 Idempotency-Key，创建 120 秒 SseEmitter。SSE 事件有 meta、stage、clarify、citation、token、done、error；token 带递增 seq。

ChatTurnService 将回合存为 ACCEPTED → RUNNING → COMPLETED / FAILED / CANCELLED，通过 lease_token、lease_until 和 attempts 防止多个 Worker 同时提交结果。SSE 断开时取消 token，并向模型和专家任务传播。

3. 路由：模型建议不直接等于执行命令

IntentRouter 输出 scope、intent、alternative、confidence、retrieval facets 和 retrieval hint。解析层验证枚举、范围、mixed 子意图、facet 白名单以及 scope/hint 一致性。

行为门槛结果
跳过检索越界置信度 ≥ 0.92、未降级、无领域信号skipRetrieval=true
多跳领域内、置信度 ≥ 0.70、无歧义、意图 margin 不窄allowMultiHopEscalation=true
澄清主次意图差距 < 0.15 或存在竞争意图SSE clarify

4. 混合 RAG：三条通道解决三类问题

FusedRetriever 同时运行 Dense、Sparse 和 Graph，再做 RRF 融合、去重和可选 Rerank。

RRF(node) = Σ 1 / (K + rank)，K = 10
expandedScore = parentScore × 0.85 × relationWeight × edgeConfidence

Graph 扩展受关系类型、方向、状态、置信度、每源邻居数、总扩展数及 user/tenant scope 限制。Rerank 候选池最多 12 条，只用于资源寻找类 Query；Rerank 失败则保留 RRF 原排序。

5. 多跳检索：有上限的证据扩展

AgenticRetriever 只有在 RoutingPolicy 允许时才进入多跳。每一跳合并“当前 Query 检索”和“上一跳图前沿扩展”，最多 3 跳。

Hop 1 = 1.00；Hop 2 = 0.60；Hop 3 = 0.36（0.6^(hop-1)）
控制点实现目的
候选池max(topK × 2, 10)给后续新证据留空间
前沿扩展只扩展上一跳派生节点保留 A → B → C 真实路径
Judgesufficient + follow-up JSON证据足够时提前停止
防循环normalized query 集合拒绝重复改写
失败非法 JSON/异常 → stop保留已有证据

6. 上下文工程：预算优先级与缓存顺序分离

ContextPlanner 管理 rules、profile、episodes、summary、evidence，总系统上下文预算是 2600 token。

规划器先按 section floor 分配，再按优先级使用剩余预算，同时记录 originalTokens、allocatedTokens 和 dropped。证据 marker 被截断时，相应 S# 不进入可引用集合。

7. 专家协作：共享 Briefing，局部失败

ExpertRunner 并发执行 resume、interview、planning 等专家。所有专家拿到相同的 Briefing：原问题、用户画像、记忆、简历摘要、Evidence 和 graph path。

结构化输出

建议数组、confidence、citations 通过 Schema、长度和范围检查。

引用闭环

专家只能引用当前 Briefing 的 S1…SN，S99 会被拒绝。

取消传播

单专家超时或用户取消只影响对应 Future。

聚合降级

Aggregator 失败时确定性拼接已完成专家内容。

8. Tool Loop：模型请求工具，后端重新验权

resolve → agent permission → DTO → Bean Validation → L2 confirmation → idempotency claim → timeout → audit

JdbcToolIdempotencyStore 以 (user_id, tool, idempotency_key) 唯一占用执行权。已完成结果直接复用，并发重复调用拒绝；失败释放 RUNNING；过期记录回收。

9. 记忆：授权、可撤销、可降级

LongTermMemoryService 先召回 Local Episode，再在 Mem0 enabled、用户 consent、outbox 允许读取且 circuit breaker 放行时访问远程。远程失败回退本地，本地失败则无记忆继续回答。

机制实现细节
合并本地+远程去重，按 relevance 排序，最多 5 条；open items 加 0.05。
去重canonical 文本 + bigram Jaccard，阈值 0.88，不额外调用 Embedding。
防污染原始问答不直接双写 Mem0，必须先经过结构化记忆准入。
遗忘事务内失效 generation、删除本地、关闭授权、远程删除入队。

10. 引用护栏：完整性和忠实度分两层

CitationGuard 先正则提取 [S#]，检查编号存在、是否越界、是否有对应证据；再用结构化 Judge 判断事实 claim 是否被证据支撑。最多 20 claims、10 条 evidence。

状态语义处理
verified引用存在且得到支撑正常展示
unsupported引用存在但支撑不足回答保留，记录 issue
invalid_reference编号越界或 Judge 生成非法编号独立完整性失败
unavailable护栏模型失败不阻断主回答

11. LLM Gateway：Purpose、预算、并发和 fallback

LlmGateway 统一 Embedding、JSON、流式生成、Rerank 和 Judge。每次调用声明 CHAT、ROUTER、EXPERT、JUDGE、EMBED 或 RERANK，不同 Purpose 使用独立超时、输出上限和重试配置。

原子预算

外呼前向 llm_turn_budget 和 llm_daily_budget 预留 Token。

并发门控

统一 acquire/release，防止专家扇出耗尽供应商资源。

故障回退

JSON 主模型失败后尝试 fallback endpoint/model。

用量结算

actual = min(reserved, providerReportedActual)。

12. 安全、状态与可观测性

浏览器认证使用 HttpOnly Cookie，写请求使用双提交 Cookie 的 X-CSRF-Token。AuthContext 提供 userId/tenantId，并把 scope 传给向量和图谱查询。Trace 记录路由、检索、专家、聚合、生成和异步任务耗时；日志优先保存状态、耗时、摘要或 hash，避免泄漏简历与回答原文。

13. 评测闭环：指标、Badcase、门禁

evals/rag_testset.json 保存带 Gold 节点的回归集，比较 vector_only、fused、fused_rerank 和 agentic，记录 Hit@K、Recall@K、MRR@K、P50/P95、路由 Macro-F1 和引用质量。失败样本按 gold_not_retrieved、multi_hop_miss、job_skill_coverage_gap、resource_type_mismatch、execution_error 聚类；完整集通过门禁后才允许 releaseEligible=true。

答辩总结：系统的价值不是让模型“自由发挥”，而是让它在有限候选、有限预算、有限步骤和可审计状态中稳定地产生可解释结果。

14. 关键实现拆解：数据库、调用边界和伪代码

14.1 数据库为什么承担可靠性

PostgreSQL 不只是业务数据存储，还承担了几个必须跨进程一致的状态：chat_turns 保存 durable 回合，tool_idempotency 防止副作用重复执行，llm_turn_budget 与 llm_daily_budget 防止并发超额，memory outbox 保存远程同步意图，structured_output_events 保存模型契约错误。

这些表都通过 Flyway 版本化迁移演进。例如可靠知识导入、租户范围、会话加密、记忆墓碑、工具审计、结构化输出事件和 durable chat turn 都是独立迁移。这样可以审查每次 schema 变化，也能保证新环境按相同顺序重建。

14.2 模型调用的统一边界

reserve(traceId, estimatedTokens);
acquire();
try {
result = provider.call(purpose, timeout, messages);
recordUsage(traceId, purpose, result.usage());
} finally {
settle(traceId, reserved, actual);
release();
}

所有 Embedding、JSON、流式生成和 Rerank 都经过 LlmGateway。因此业务服务不需要知道具体供应商，也不能绕开预算、并发门控和 usage 记录。

14.3 一次多跳循环的伪代码

query = originalQuery;
evidenceById = {};
for hop in 1..3:
queryHits = fused.retrieve(query, topK * 2);
graphHits = frontier.isEmpty ? [] : fused.expandFrontier(frontier);
hopHits = mergeAndDedupe(queryHits, graphHits);
for hit in hopHits:
evidenceById[hit.id] += hit.score * pow(0.6, hop - 1);
if hop == 3: break;
verdict = judge(originalQuery, query, strongestEvidence);
if verdict.sufficient: break;
query = sanitizeFollowup(verdict.followupQuery);
results = sortAndLimit(evidenceById, topK);

15. 与其他常见方案对比：收益和代价

这里的对比不是简单判断“谁更先进”，而是说明这个项目为什么选择更复杂的组合，以及复杂性换来了什么。

方案优点不足本项目选择
直接 Chat + Prompt实现最快、链路短、延迟低没有事实来源、容易幻觉；无法解释路由和失败；工具副作用危险只作为最底层生成能力，外面增加检索、引用和治理
纯向量 RAG组件少、语义召回自然、容易上线专有词和缩写容易漏；岗位→技能→前置知识关系表达弱Dense 保留，同时增加 pg_trgm 和 Neo4j
向量 + Cross-Encoder 全量重排候选相关性常有提升每次都增加延迟和成本；可能压低需要图关系才能理解的节点只对资源推荐 Query 启用 Rerank，失败回到 RRF
无边界 Agent灵活，模型能自行规划步骤和工具循环、成本、越权、不可复现和难测试只开放受控 Tool Loop，最多 3 步，工具必须注册和验权
所有历史直接塞 Prompt开发简单，短期上下文完整Token 爆炸、旧错误污染、缓存命中差、证据被挤掉窗口、摘要、Episode 和 ContextPlanner 分层预算
原始问答直接写长期记忆实现简单，记忆看起来“很聪明”幻觉、注入和敏感信息会持久化；删除难保证结构化准入、generation、outbox、墓碑和可删除机制
微服务拆分所有模块独立扩缩容，团队边界清晰本项目阶段会增加部署、网络和分布式事务复杂度先在模块化 Spring Boot 内保留清晰接口，热点再拆

15.1 主要代价

延迟代价

路由、Embedding、稀疏检索、图扩展、Rerank、Judge 和 Citation Guard 都可能增加耗时，因此项目使用条件触发、异步验证和 P50/P95 评测。

运维代价

PostgreSQL、Neo4j、LLM Provider、可选 Mem0、对象存储和 Flyway 都需要健康检查、熔断、迁移和备份。

数据代价

Gold 节点、图谱关系、来源状态、租户范围和人工标注都需要维护，否则系统会把数据问题误判成算法问题。

工程收益

失败可定位、模型可替换、工具可审计、记忆可删除、检索可回归，适合学习求职这种连续使用和高解释性场景。

16. 当前边界与后续演进

这套设计不是没有缺点。多跳和专家并发会增加成本；Citation Guard 的语义判断仍依赖 Judge 模型；图谱质量决定关系检索上限；远程记忆同步需要后台任务最终完成；前端必须正确处理 SSE 断线和取消状态。

后续可以沿三条方向演进：第一，基于线上 trace 和评测结果做路由置信度校准；第二，将 Evidence、graph path 和 citation verification 结果做更细粒度的人工抽检；第三，把已经出现明确瓶颈的 ingestion、retrieval 或 evaluation worker 独立扩展，而不是一开始就把所有模块拆成微服务。

适用判断：如果需求只是 FAQ，直接 Chat 或纯向量 RAG 更划算；如果需求包含个人画像、岗位关系、可执行工具、长期记忆和高可信引用，这个项目的额外治理复杂度才有回报。
